The extension talks to one endpoint. Everything about it lives in `api/hono/src/routers/ratings.ts` and three modules beside it in `lib/`: `imdb.ts` (the dataset rows, the keep filter, and the matching, all pure), `lookup.ts` (query keys, spelling variants, batch alignment, pure) and `ratings.ts` (the one query per batch). There is no third-party ratings API behind it and no cache in front of it.

## `POST /api/v1/ratings`

```json
{
  "titles": [
    { "title": "Rick and Morty", "type": "series" },
    { "title": "Alpha", "type": "movie", "year": 2026, "runtime": 140 }
  ]
}
```

Up to 50 titles per call. `type` (`movie` or `series`), `year`, and `runtime` (minutes) are optional in the request, but a title is only ever matched when its `year` is stated, and `type` and `runtime` are what tell a remake, a same-name film from another country, or a show's namesake apart. The answer is one entry per title, in the order asked:

```json
{
  "data": {
    "ratings": [
      {
        "found": true,
        "imdbId": "tt2861424",
        "imdbRating": 9.1,
        "imdbVotes": 640123,
        "metascore": null,
        "poster": null,
        "reason": null,
        "rottenTomatoes": null,
        "title": "Rick and Morty",
        "type": "series",
        "year": 2013
      },
      {
        "found": true,
        "imdbId": "tt28363783",
        "imdbRating": 6.1,
        "imdbVotes": 12000,
        "metascore": null,
        "poster": null,
        "reason": null,
        "rottenTomatoes": null,
        "title": "Alpha",
        "type": "movie",
        "year": 2025
      }
    ]
  }
}
```

`title` and `year` in an answer are IMDb's, so a card that said 2026 can come back as 2025 (a regional release a year late). `metascore`, `poster`, and `rottenTomatoes` are always null: they are kept for one release so the v0.0.1 extension, which still reads them, does not paint "undefined". A title the index cannot match with certainty comes back with `found: false`, the IMDb fields null, and a `reason`: `unstated` (no year to check against), `unknown` (no IMDb title under any spelling of the name), `unmatched` (namesakes exist but none fits the stated kind, year, and runtime), or `ambiguous` (candidates fit but none is certain). A title it knows but nobody has rated yet comes back `found: true` with `imdbRating: null` and `reason: "unrated"`; with a score, `reason` is null. The extension's popup lists a tab's scoreless titles by these reasons. `GET /api/v1/ratings?title=Dune&year=2021` answers one title the same way, for a quick check from the browser or curl. The interactive reference at [`/api/docs`](/api/docs) has both.

## How a title is matched

The index holds every IMDb film, TV film, special, series, and mini-series that is rated or from this year or last, and every short and video with 100+ votes (about 620,000 titles), each under its primary and original name, and, for a well-known title (1,000+ votes), the alternate names IMDb displays in English-speaking regions or worldwide ("Dune" for "Dune: Part One", "Marvel's Daredevil" for "Daredevil"; about 40,000 of them, flagged as alternate) and, for the same well-known titles, the bare name before a subtitle's colon or dash ("Bleach" for "Bleach: Thousand-Year Blood War", flagged the same way), all keyed by a spelling that folds case, width, diacritics, punctuation, and `&`. A lookup fetches the candidates for every spelling of every title in the batch in one query (as written, then without a parenthetical qualifier, then without a subtitle after a colon, then the subtitle alone ("Half Bad: The Bastard Son & The Devil Himself" is IMDb's "The Bastard Son & the Devil Himself"), each also with its leading English article dropped or "The" put on, since "Devil's Advocate" is IMDb's "The Devil's Advocate", and with a standalone number written the other way, since "Fear Street Part 1: 1994" is IMDb's "Fear Street: Part One - 1994"), and decides per title in `resolveTitle`, stopping at the first spelling any candidate fits:

1. A candidate fits when the kind agrees, a film's year is within one of its release, and a title that fits under its own name outranks any that fit only under an alternate name (an alternate-name candidate is taken only when it alone fits), a series' run contains the stated year (a year either side, since Netflix states a show's latest season; a run IMDb has not closed reaches the present only for a show with 1,000+ votes), and a film's runtime is within ten minutes when both are known (Netflix's cut of a film can run ten minutes short of IMDb's). The looser spellings are tried only while the index knows nothing under the name as written or with its article moved (a film under an article variant must match the year exactly), so a spin-off the index lists (even misdated) never falls through to its parent; under the unsubtitled spelling a film's year must match exactly and a series must be well known and running, and under the subtitle alone the title must be a work of its own from the stated year.
2. Nothing is taken without a stated year (a search result), however unique the name: a new title IMDb lists under its original name would wear a namesake's score (Netflix's Mexican "Lovesick" of 2026 against the British series). The name is still looked up, so the answer says whether the index knows it (`unknown`) or only lacks a year (`unstated`). With a year, once any candidate can be checked against what was stated, the ones that cannot (no year on IMDb, no runtime) drop out, but still veto a pick they out-vote three to one. A film and a series of one name with no kind stated are an ambiguity.
3. One candidate left is the answer. Several are ranked by closest runtime (films), then votes, and the best is taken only when something separates it: a runtime closer by three minutes or more, or 100+ votes that are three times the runner-up's, which is never enough under the unsubtitled spelling and never while a candidate in the running is too new to have earned its votes (unrated, or under 100 votes and from this year or last) and as close to the stated year as the best: a title that new is as likely Netflix's as its popular twin, unless it sits a year off the one Netflix states while the twin sits on it, or a stated runtime fits the twin at least as closely (a namesake of the same year and length is a duplicate listing).

A wrong score is worse than none, so every ambiguity is a miss. The [imdb-sync skill](https://github.com/nrjdalal/rate-my-ott/blob/canary/.agents/skills/imdb-sync/SKILL.md) is the procedure for diagnosing one.

## The index

`bun run imdb:sync` (`api/hono/src/jobs/imdb-sync.ts`) streams IMDb's `title.ratings`, `title.basics`, and `title.akas` datasets (about 750 MB gzipped) and upserts them into `imdb_title` and `imdb_name`, writing only rows that changed, dropping the spellings a renamed title no longer answers to, and pruning titles that left the dataset, all in one transaction so a night lands whole or not at all; a full rebuild takes a minute or two locally and a few minutes from CI. In production the `auto-imdb-sync` workflow runs it every day at 14:30 UTC, after IMDb's own refresh. The two tables take about 210 MB.

## `GET /api/v1/ratings/status`

What the index holds and when it was last rebuilt: `{ "data": { "index": { "akas": 41093, "finishedAt": "2026-08-29T14:33:00.000Z", "names": 760902, "titles": 619222 } } }`, or `"index": null` while it has never been built. Each rebuild writes its record (`imdb_sync`) inside its own transaction, so the newest row always describes the index that is serving; a rebuild that failed leaves no row, which is how a stale index shows. The extension's popup reads it ("IMDb index: 619K titles, refreshed 2 hours ago").

## Errors

The usual envelope, `{ "error": { "code", "message" } }`, with one code of its own: `503 SERVICE_UNAVAILABLE` while the index is empty (the sync has not run yet). `400 VALIDATION_ERROR` carries the failing fields.

## Calling it with types

Both the web app and the extension use the Hono RPC client, so the request and response types come from the route itself:

```ts
import { apiClient, unwrap } from "@/lib/api/client"

const { data, error } = await unwrap(
  apiClient.v1.ratings.$post({ json: { titles: [{ title: "Rick and Morty" }] } }),
)
```
